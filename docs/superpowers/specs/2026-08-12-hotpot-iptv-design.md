# hotpot-iptv — Design Spec

**Date:** 2026-08-12
**Status:** Approved design, pending implementation plan

## What it is

A self-hosted FFmpeg orchestrator, written in Go, that turns a media library on an
SMB share into linear 24/7 IPTV channels delivered as HLS over HTTP, with full
multi-audio-track and subtitle support. Managed through a built-in web UI. Runs in
Docker with NVENC hardware encoding.

## Decisions (agreed during brainstorming)

| Topic | Decision |
|---|---|
| Output format | HLS over HTTP (single Go server serves playlists + segments) |
| Channel model | Linear 24/7: playlist plays continuously, loops forever |
| Scheduling | Continuous loop; position persisted; resume at start of the item that was playing |
| Transcoding | Always transcode video via NVENC (Quadro M620 → H.264 output only; HEVC sources decode on CPU) |
| SMB access | CIFS volume mounted into the container at `/media`; app and FFmpeg see plain files |
| Persistence | PostgreSQL + sqlc + Atlas (workspace standard) |
| Track policy | Auto-include every audio track and every text subtitle track found by ffprobe, labeled by language |
| Web UI scope (v1) | Channel management + SMB browser, status dashboard, HLS.js preview player, M3U + XMLTV export |
| Orchestration | One FFmpeg run per playlist item; Go owns all HLS playlists (Approach 1) |

## Architecture

Two containers via docker-compose: **app** (Go binary + FFmpeg) and **postgres**.
SMB share mounted read-only at `/media` (CIFS volume, credentials from `.env`).
HLS output written to tmpfs at `/streams`. App container uses the NVIDIA runtime.

Three planes inside the Go binary:

- **Control plane** — chi HTTP server: JSON API (channel CRUD, library browsing,
  status), web UI (html/template + Tailwind CDN + vanilla JS), M3U/XMLTV export.
- **Engine plane** — supervisor owning one *channel runner* goroutine per running
  channel. Runner loop: probe current playlist item → run FFmpeg on it → feed
  segments to the HLS playlist manager → advance to next item, persist position →
  loop forever.
- **Delivery plane** — handlers serving `/streams/{slug}/…` (master playlist,
  media playlists, segments) from tmpfs. All playlist files are generated by Go,
  never by FFmpeg.

## Per-file FFmpeg pipeline

One FFmpeg invocation per playlist item:

- **Video** → `h264_nvenc`, forced IDR frames every 4 s
  (`-forced-idr-frames`), segmented MPEG-TS via the `segment` muxer with
  sequential numbering. Decode happens on CPU when NVDEC can't handle the source
  codec (GM107 has no reliable HEVC decode); the 24/7 cost — encoding — stays on GPU.
- **Each audio track** → its own output: AAC 160 kbps stereo, segmented MPEG-TS,
  same 4 s cadence, labeled from the source language tag (fallback `und`).
- **Each text subtitle track** (srt / ass / mov_text; bitmap formats like PGS are
  skipped in v1) → one whole-file `.vtt` per track, then a pure-Go **VTT
  splitter** cuts cues into 4 s segments aligned with the video timeline.
- External `.srt` files with the same basename as the video are included as
  additional subtitle tracks.

Go tracks encode progress via the `-progress` pipe and watches the output
directory; as segments land, it appends them to the live media playlists.

## HLS playlist manager (Go-owned state machine)

Pure-logic component, no I/O of its own:

- One **media playlist** per rendition (video, audio × N, subtitles × N) plus the
  **master playlist** with `EXT-X-MEDIA` audio/subtitle groups.
- `EXT-X-DISCONTINUITY` at every file boundary; `EXT-X-DISCONTINUITY-SEQUENCE`
  bumped as boundaries slide out of the window.
- Sliding live window (default 30 segments × 4 s), monotonic
  `EXT-X-MEDIA-SEQUENCE`, expired segments deleted from tmpfs.
- **Heterogeneous files:** the rendition set is fixed per channel session (union
  of tracks across the playlist, computed from the probe cache). When the current
  file lacks a rendition (e.g. no Thai audio), the runner emits **silent AAC /
  empty VTT filler segments** for it. Renditions never appear or disappear while
  clients are connected; the master playlist stays stable.

## Data model (Postgres + sqlc + Atlas)

- `channels` — id, name, number, slug, enabled, output settings (resolution,
  bitrate; global defaults with per-channel override).
- `playlist_items` — channel_id, position, path relative to `/media`.
- `media_files` — probe cache keyed by (path, mtime, size): duration, video
  codec, audio tracks (index, language, codec), subtitle tracks. Probed when
  added to a playlist; re-probed when mtime/size change.
- `channel_state` — channel_id, current item position, item started_at, runner
  status. Resume after restart = start of the item that was playing.

## HTTP surface

- `/api/v1/channels` CRUD; `POST /api/v1/channels/{id}/start|stop`;
  `GET /api/v1/channels/{id}/status`.
- `/api/v1/library?path=` — browse `/media`: directories, video files, probe
  summary for known files.
- `/streams/{slug}/master.m3u8`, media playlists, segments — CORS-open.
- `/playlist.m3u` — all enabled channels with `tvg-id`/`tvg-name`.
- `/epg.xml` — XMLTV computed forward ~24 h from each channel's current position
  through the looped playlist, using cached durations.
- Web pages: **Channels** (list + editor with SMB-browser modal), **Dashboard**
  (status, now playing, restart counts, start/stop), **Preview** (HLS.js with
  audio/subtitle switching).

Repo layout follows the workspace API + CQRS-core convention:
`api/<feature>/{server.go,service,http}` + `internal/<feature>/{domain,app}`,
plus `internal/engine` (supervisor/runner), `internal/ffmpeg` (probe, command
builder, process runner), `internal/hls` (playlist state machine, VTT splitter),
`internal/epg`, `internal/web`, `templates/`.

## Error handling

- FFmpeg non-zero exit → log stderr tail to a channel event log, retry the item
  once, then skip to the next item. 5 consecutive item failures → channel enters
  `error` state (dashboard-visible), auto-retry with exponential backoff capped
  at 5 min.
- SMB stall: no `-progress` advance for 30 s → kill FFmpeg, retry item.
- File missing at play time → skip item, mark errored in the UI.
- App restart → supervisor restores running channels from `channel_state`;
  clients see a short gap, then a fresh HLS session.

## Docker & config

- Multi-stage Dockerfile: Go build (`CGO_ENABLED=0`), final stage from an
  FFmpeg-with-NVENC base image.
- Compose: app (`runtime: nvidia`, CIFS volume `/media`, tmpfs `/streams`, port
  8080) + postgres 16 (named volume).
- Config via viper `AutomaticEnv` into a typed struct: `PSQL_URL`, `MEDIA_PATH`,
  `STREAMS_PATH`, `PORT`, `SEGMENT_SECONDS` (default 4), `WINDOW_SEGMENTS`
  (default 30), encoder defaults (default 1080p, 5 Mbps H.264).

## Testing

- **Unit (bulk of coverage):** HLS playlist state machine (golden m3u8 files —
  discontinuities, window slide, filler renditions), VTT splitter, EPG
  computation, FFmpeg command builder (golden argument lists per probe fixture).
- **Integration:** testcontainers Postgres for sqlc queries and channel state
  transitions; run with `go test -p 1`.
- **End-to-end (scripted in Taskfile, run manually):** generate synthetic
  multi-track MKVs (`testsrc` + two audio languages + srt), run a channel,
  verify the HLS output with ffprobe and the preview player. Encoder selection
  sits behind the command-builder interface so CI and GPU-less dev boxes use
  `libx264` while production uses NVENC.

## Out of scope for v1

- Bitmap subtitle (PGS/VOBSUB) OCR or burn-in
- Adaptive bitrate ladders (single video rendition per channel)
- Anchored wall-clock scheduling and shuffle channels
- User accounts / auth on the web UI (LAN-trusted appliance)
- DVR / catch-up / recording
